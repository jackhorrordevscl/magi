## Key Learnings

1. `magi.config.json`'s existing `loadConfig()` in `main.ts` throws on invalid JSON (a bare `JSON.parse(...) as MagiConfig` cast, per spec Key Learning #3); the new `evaluator-config.ts` loader is explicitly required to diverge from that pattern and never throw, so it cannot simply delegate to or copy `loadConfig`'s read path.
2. The three named evaluators' hardcoded default models (`openai/gpt-oss-120b`, `llama-3.3-70b-versatile`, `llama-3.1-8b-instant`) are all Groq-specific IDs — applying any of them to a different backend after a `backend` override would guarantee a non-2xx failure, which is why the backend-aware model default (design decision 4, `model = cfg.model ?? (backend === defaults.backend ? defaults.model : undefined)`) is load-bearing, not a nice-to-have.
3. `createMelchior`/`createBalthasar`/`createCasper` are explicitly excluded from config-reading (design decision 2) because `tests/gating/named-evaluators.test.ts` already asserts their hardcoded default models via direct `create*({ client })` calls; only the module-level default export (`export const melchior = ...`) is resolver-built, keeping that existing test suite unchanged as a hard constraint, not a convenience.
4. `main.ts` and `claude-code-hook/index.ts` need zero edits because both already type-import `melchior`/`balthasar`/`casper` as `EvaluatorPort` (not the concrete `GroqEvaluator` type) at their existing consumption sites (`main.ts:157`, `index.ts:127`) — config reaches both entrypoints transitively through the widened default-export type, which is the only type change this capability makes.
